# Plumbing — Hidden Machine

How this project's rooms reach builders, Klutz and other projects. Only the rooms whose own file names it read it.

## Messaging

Cross-session messaging (`SendMessage`) between rooms and builders is forbidden, with three exceptions: an idle notice (`notify_when_idle`, no text); a coordinator asking its own builder where it is, where the reply is informational and the status file stays the record; and a heads-up pointing a room at a file that changed, never carrying a decision. Never by message: answers to a builder, approvals or commit authorizations, prompts or instructions.

## Klutz

Klutz wakes the coordinator with one line in its pane when something happens to one of this project's dispatches. `KLUTZ blocked … read=<file>`: a builder wrote a `.blocked.md`; read it, and if the question is about what the coordinator's own prompt meant, draft an answer in `answers/<prompt filename>` for the user to send with `klutz answer <dispatch> --file answers/<name>`; otherwise tell the user what it asks. `KLUTZ done … read=<status file>`: a dispatch finished; read the status file and record it. `KLUTZ mismatch … read=<status file>`: the status file's `dispatch:` or `input_hash:` disagrees with the dispatch, so Klutz parked it; tell the user, whose way out is `klutz dismiss <dispatch>` or `klutz resend <dispatch>`, and never record it as done. `KLUTZ idle`: the builder stopped with neither a status file nor a blocked file (an API error, say); tell the user, whose way out is `klutz resend <dispatch>`. Never type into a builder's pane, and never send a prompt into a builder's session.

`answers/<prompt filename>` holds the coordinator's draft answer to a builder's blocked file; the user reads it and sends it with `klutz answer`, which is what makes it the user's answer (the Lines' exception aside). Klutz never scans `answers/`.

Standing exception to any Line that keeps answers with the user: the coordinator may send its own draft from `answers/` with `klutz answer` (a) when the answer only cuts scope or picks the builder's more conservative option, or (b) for any option when the repo carries a rollback tag the user set for the run, in which case the answer tells the builder to commit its work as it stands first, then build the chosen option on top. Anything else waits for the user. A coordinator-sent answer opens with `Coordinator answer, not the user's (Line exception):`, so the record says who sent it, and gets a Log line in `ROADMAP.org`.

Klutz clears a native Claude builder it reuses before each new prompt, so write `klutz-request: 2` and `context: keep` in the header only on a prompt whose body continues the previous dispatch to the same builder (a step 2 of 3), and leave them off otherwise; the field is defined in Klutz's `docs/envelope.md`, not here.

## Status files

**Status** `status/<prompt name>.md`: what was run, what passed — naming both the targeted check and the full suite — the evidence (paths, output, exit codes, screenshots), and what the prompt got wrong, if anything, under Facts that change the brief, ending `END OF <filename>`. Blocked instead of done is the same name with `.blocked.md`: the question, what it is blocked on, and deliberately no `END OF`, so an unfinished answer is visibly unfinished; the builder deletes it when it proceeds.

## Inbox

Inbox: `<org root>` is `$JOURNO_ORG_ROOT` when that is set (a test sandbox; never fall back to Dropbox then), else `org` in this machine's Dropbox folder: the path Dropbox's own `info.json` gives (`personal`, else `business`; on WSL, Windows' Dropbox, found under the home Windows names, `cmd.exe /c echo %USERPROFILE%` through `wslpath`), and with no `info.json`, `Dropbox` in that home, or `~/Dropbox`. `<user>` is the login name, `$USER`. This project's inbox is `<org root>/inbox/hiddenmachine/`; if that folder doesn't exist, the inbox is empty, which is not an error. The global brainstorm sends the user's answers there. It sends ideas there too: the idea room takes each complete one into `ideas/` at start and never edits a delivered idea; changes come back as a new file. At start, the idea room takes each file there that ends with its `END OF` line: an answer (`*-answer-*.org`) goes into `reports/` beside the report it answers, and a file that is neither an idea, an answer nor a handoff (a transcript, a video, a screenshot) into `sources/`. Such a source carries no `END OF` line, so the idea room takes it only once a complete idea or answer beside it names it by filename; an unnamed one stays in the inbox and the idea room tells the user. It then deletes the inbox copy, and skips Dropbox conflicted copies, telling the user they're there. After each report, the idea room writes one notice to `<org root>/inbox/<user>/` per `spec/inbox-notice.org` in `bpjohnson/mabel`, carrying only what is still open: questions the user answered in this conversation go in the report, not the notice. If the user was in the conversation and nothing is left open, it writes no notice. Apart from the fourth inbox case below, those are the idea room's only writes outside `reports/` and `sources/`. A handoff is a delivery another project's coordinator writes into this inbox once work this project asked for is done, carrying facts only, per `spec/handoff.org` in `bpjohnson/mabel`; at start the idea room files each `*-handoff-*.org` whose last non-blank line is `END OF <its own filename>` into `reports/` as it does an answer, and the coordinator reads it like any report. The coordinator writes outside this folder in four inbox cases only: a notice to `<org root>/inbox/<user>/` with `#+KIND: request` and `#+TO: <target slug>`, per `spec/inbox-notice.org`, when this project needs something from another project that isn't its child and the fourth case doesn't cover (the global brainstorm routes it only on the user's yes); a delivery `<org root>/inbox/<requester>/<date>-handoff-<slug>.org`, per `spec/handoff.org`, once work another project asked for is done, carrying facts and never a request back; and, when this project is another's parent (the child's heading in Mabel's project list (the file `projects_file` names in Mabel's `personal.json`, else `$MABEL_CONFIG/projects.org`) carries `:PARENT: hiddenmachine`), a request delivered straight into that child's inbox as an idea, with no request notice, per `spec/inbox-notice.org` Requests in `bpjohnson/mabel`. A request to this project's parent still goes through a notice, unless the fourth case applies. The fourth case is every room's, not only the coordinator's, and an exception to each room's write rule: when the user names another project in a room and asks for something to go to it, the room delivers the user's words straight into that project's inbox as an idea if Mabel's project list (the file `projects_file` names in Mabel's `personal.json`, else `$MABEL_CONFIG/projects.org`) gives it an idea room, and otherwise writes the `#+KIND: request` notice, per `spec/inbox-notice.org` Requests in `bpjohnson/mabel`.
